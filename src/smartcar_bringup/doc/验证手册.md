# smartcar_bringup 验证手册

本文档说明如何验证四轮麦克纳姆小车控制栈，覆盖 **WSL2 mock 仿真**（无硬件）
与 **树莓派实机** 两种场景。命令均可直接复制执行。

---

## 1. 前置：编译与环境

```bash
cd /mnt/d/Projects/smart_car_robot        # 树莓派上为 ~/smart_car_robot
colcon build --symlink-install
source install/setup.bash
```

- WSL2 开发机：跳过硬件，使用 `use_mock_hardware:=true`（默认）。
- 树莓派实机：需先把用户加入 `dialout` 组并确认串口设备名（见根目录 README §4.2）。

## 2. WSL2 mock 仿真验证:2026-08-08 验证通过

### 2.1 启动

```bash
ros2 launch smartcar_bringup smartcar.launch.py
# 等价于 use_mock_hardware:=true
```

启动后应在日志看到（先后两次 "Successfully switched controllers"）：

```
[controller_manager] Loaded hardware 'smartcar_system' from plugin 'mock_components/GenericSystem'
[spawner] Configured and activated joint_state_broadcaster
[spawner] Configured and activated mecanum_drive_controller
```

> 说明：`joint_state_broadcaster` 能激活，证明 8 个状态接口（4 关节 ×
> position/velocity）已注册可用；`mecanum_drive_controller` 能激活，
> 证明它成功 claim 了 4 个 velocity 命令接口。任一接口命名不符都会导致
> 控制器激活失败并报错。

### 2.2 查看控制器与接口（另开一个终端）

```bash
source install/setup.bash

```

### 2.3 里程计方向验证（前进 / 横移 / 旋转）

**关键提示**：Jazzy 的 `mecanum_drive_controller` 订阅的是
`geometry_msgs/msg/TwistStamped`（带时间戳），话题为
`/mecanum_drive_controller/reference`；而 `teleop_twist_keyboard` 默认发布
不带时间戳的 `Twist`。因此遥控必须加 `-p stamped:=true` 并 remap 话题。

#### 方式 A：键盘遥控

```bash
ros2 run teleop_twist_keyboard teleop_twist_keyboard \
  --ros-args -p stamped:=true \
  -r /cmd_vel:=/mecanum_drive_controller/reference
```

- `i` 前进 → `/mecanum_drive_controller/odometry` 的
  `twist.twist.linear.x` 为正。若启动 `use_ekf:=true`，
  `/odometry/filtered` 的 `pose.pose.position.x` 应增大。
- 麦轮横移键（`j`/`l` 在 holonomic 模式，先按 `b` 切换）→ `twist.linear.y` 变化。
- `k` 停。

#### 方式 B：Xbox 手柄方向键遥控

启动完整实机系统并启用手柄：

```bash
ros2 launch smartcar_bringup smartcar.launch.py \
  use_mock_hardware:=false \
  serial_port:=/dev/ttyUSB0 \
  use_joy:=true
```

手柄必须按住 LB（Button 4）才能输出速度。方向键映射如下：

| 输入 | Joy 索引 | 输出 |
|---|---:|---|
| 上 | Vertical Axis 7 = `+1` | `linear.x = +dpad_speed` |
| 下 | Vertical Axis 7 = `-1` | `linear.x = -dpad_speed` |
| 左 | Horizontal Axis 6 = `-1` | `linear.y = -dpad_speed` |
| 右 | Horizontal Axis 6 = `+1` | `linear.y = +dpad_speed` |

当前手柄的 `/joy.buttons` 长度为 11，因此方向键默认使用轴模式；Button 12/13/14/15 仅作为其他手柄的兼容映射。方向键输入优先于左摇杆平移；右摇杆不参与控制。普通方向键速度由 `config/xbox_teleop.yaml` 中的 `dpad_speed` 配置，默认值为 `0.5 m/s`；按住 RB（Button 5）后使用 `dpad_turbo_speed`，默认值为 `1.0 m/s`。

查看实时输入，确认手柄索引是否匹配：

```bash
ros2 topic echo /joy
```

完整手柄映射图见 [docs/xbox_手柄映射.png](../../../docs/xbox_手柄映射.png)，可编辑源文件见 [docs/xbox_手柄映射.drawio](../../../docs/xbox_手柄映射.drawio)。

#### 方式 C：命令行直接发布（可复制，便于自动化）

前进（+x）：
```bash
ros2 topic pub /mecanum_drive_controller/reference geometry_msgs/msg/TwistStamped \
  '{twist: {linear: {x: 0.3, y: 0.0, z: 0.0}, angular: {z: 0.0}}}' -r 10
```

横移（+y）：
```bash
ros2 topic pub /mecanum_drive_controller/reference geometry_msgs/msg/TwistStamped \
  '{twist: {linear: {x: 0.0, y: 0.3, z: 0.0}, angular: {z: 0.0}}}' -r 10
```

原地旋转（+z）：
```bash
ros2 topic pub /mecanum_drive_controller/reference geometry_msgs/msg/TwistStamped \
  '{twist: {linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {z: 0.8}}}' -r 10
```

另开终端观察里程计：
```bash
ros2 topic echo /mecanum_drive_controller/odometry
# 前进：twist.twist.linear.x  ≈ +0.3
# 横移：twist.twist.linear.y  ≈ +0.3
# 旋转：twist.twist.angular.z ≈ +0.8
```

查看 TF：
```bash
ros2 run tf2_tools view_frames
# 或
ros2 topic echo /tf
```

默认 `use_ekf:=false` 时，底盘控制器只发布
`/mecanum_drive_controller/odometry`，不会发布 `odom → base_footprint`
动态 TF。启用 `use_ekf:=true` 后，才应出现
`odom → base_footprint → base_link` 链路。

### 3.2 台架静态启动与 EKF 定位验证（2026-08-05）

> 安全前提：车辆放在台架上，四轮悬空；测试人员可以立即断开电机电源。台架测试只能验证轮速、里程计和融合链路的一致性，不能验证实际地面位移精度。

#### 3.2.1 启动与静止判据

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 launch smartcar_bringup smartcar.launch.py \
  use_mock_hardware:=false \
  serial_port:=/dev/ttyUSB0 \
  use_ekf:=true \
  use_joy:=false
```

另开一个终端，在不发送任何速度指令时采集原始与融合里程计：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 topic echo /mecanum_drive_controller/odometry --once
ros2 topic echo /odometry/filtered --once
ros2 topic echo /imu/data_raw --once
```

静止时原始里程计的 `twist.twist.linear.x/y`、`twist.twist.angular.z` 应接近零。融合里程计的速度也应在 IMU 的噪声范围内接近零；若融合速度持续偏离零，先检查 `ekf_odom.yaml` 是否只融合 `yaw` 角速度，并确认没有在 IMU 未发布有效姿态时启用重力移除。

#### 3.2.2 MPU6050 静止标定

MPU6050 安装约定为右手系：`+x` 向前、`+y` 向左、`+z` 向上，芯片中心等同于车体坐标原点。标定时必须保持车辆和传感器静止且 `+z` 向上：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash

ros2 run ros2_mpu6050 ros2_mpu6050_calibrate
```

将输出的六个偏置写入单独的 `src/ros2_mpu6050/config/calibration.yaml`，不要改动默认 `params.yaml`。其中 `accel_z_offset` 已由标定工具扣除标准重力加速度 `9.80665 m/s²`；静止平放时不能直接把 `+z` 轴的加速度均值作为偏置，否则驱动会错误地消除重力。

重新启动后检查参数是否已覆盖默认配置：

```bash
ros2 param get /mpu6050_sensor gyro_z_offset
ros2 param get /mpu6050_sensor accel_z_offset
```

#### 3.2.3 台架受控运动

只执行一个方向，观察话题后先发送零速度，再进入下一个方向：

```bash
# 前进
ros2 topic pub --times 10 --rate 10 \
  /mecanum_drive_controller/reference geometry_msgs/msg/TwistStamped \
  "{twist: {linear: {x: 0.05, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}}"

# 停止
ros2 topic pub --once /mecanum_drive_controller/reference \
  geometry_msgs/msg/TwistStamped \
  "{twist: {linear: {x: 0.0, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 0.0}}}"
```

前进时原始里程计的 `twist.twist.linear.x` 应为正；横移时 `linear.y` 的符号应符合坐标系；原地旋转时 `angular.z` 应为非零。停止后，原始和融合里程计速度都应回到接近零。依次将上面命令中的 `linear.x` 改为 `linear.y=0.05`，或改为 `angular.z=0.2`，即可完成横移和旋转验证。

`ros2 topic pub` 的手工消息没有 `header.stamp`，控制器会记录
`Timestamp in header is missing` 并采用当前时间；这是手工测试消息的提示，
不影响本节的短时台架验证。每次方向测试结束后必须发送零速度，并确认速度
已回零再执行下一项。

#### 3.2.4 2026-08-05 台架实测记录

测试环境为树莓派 4B、`/dev/ttyUSB0`、MPU6050 地址 `0x68`，车辆四轮悬空，
启动参数为 `use_ekf:=true use_joy:=false`。启动前必须确认
没有上次异常中断残留的 `smartcar.launch.py`、`ros2_control_node`、
`ros2_mpu6050`、`web_telemetry_adapter.py`、`rosbridge_websocket` 或 `rosapi_node`
进程；多个同名节点会重复发布 IMU 和遥测，得到的结果无效。

测试结束时，应在运行 launch 的原终端按 `Ctrl-C` 后复查进程是否已退出。远程
会话被强制中断时，launch 的子进程可能没有被一并回收；此时先发送零速度，再按
上面的进程名逐项确认和停止，确认 `/dev/ttyUSB0` 不再被占用后才开始下一轮测试。

首次启动曾在 `$deadzone:1300#` 配置命令上没有收到电机板确认。停止该次失败
启动残留并重新启动后，串口配置、硬件激活和三个控制器均成功进入 `active`。
该现象只出现一次，现有证据不足以归因于固件或电机协议，因此没有修改电机协议。
若再次出现，先完全停止残留进程、检查串口是否被占用，再重试；只有持续复现时才
排查固件是否支持该配置命令。

| 项目 | 实测结果 | 判定 |
| --- | --- | --- |
| 静止 IMU | `angular_velocity.z=0.00049 rad/s`，`linear_acceleration.z=9.85656 m/s²` | 通过；重力未被错误扣除 |
| 静止原始里程计 | 位姿和 `twist` 均为 `0` | 通过 |
| 静止融合里程计 | 线速度为 `0`，初始 yaw 约 `0.017 rad` | 通过；保留可重新静态标定的微小零偏 |
| 前进轮组，`x=0.05 m/s`、3 s | 原始 `x=0.663 m`，融合 `x=0.667 m`，停止后速度回零 | 通过；台架只验证编码器积分链路，不代表地面实际位移 |
| 横移轮组，`y=0.05 m/s`、3 s | 原始 `y` 从约 `-0.002 m` 增至 `0.572 m`，融合 `y` 增至 `0.625 m` | 通过；正 `y` 为车体左方 |
| 原地旋转轮组，`z=0.2 rad/s`、3 s | 原始 yaw 约 `2.17 rad`；融合 yaw 约 `0.077 rad` | 通过；车体实际未转动，EKF 应以静止 MPU6050 的 yaw 角速度抑制悬空编码器虚假转向 |
| 停止后静置 10 s | 融合位置保持 `x=0.747803 m`、`y=0.705047 m`；速度约为 `0` | 通过；台架轮组累计位置保留是正常的历史积分结果 |

台架上轮子转动而车体不移动时，原始轮速里程计仍会累计位置和航向，这是编码器
只能测量轮子转角的物理结果。融合里程计的位置也会继承轮速速度积分，不能把其
累计位置当作车辆真实地面位移；本次修复保证的是静止时不会再由 IMU 加速度伪造
线速度，且不采用悬空轮组产生的原始 yaw 作为融合姿态。

#### 3.2.5 2026-08-06 地面直行定位排查与坐标基准修正

本次测试将车辆放到地面，仅发送前进指令，使用卷尺测量实际位移。第一次测试发现
驱动板采用四倍边沿计数，而软件按一倍计数解释：实车前进约 `0.25 m`，原始里程计
却增加约 `1.046 m`。因此完成编码器倍频修复：`count_multiplier=4`，`CPR=1040`。
树莓派重新编译并重启后，启动日志确认 `CPR=1040.0 wheel_radius=0.030m`。

修复后的固定 `5 s` 地面测试结果如下：

| 项目 | 实测结果 | 判定 |
| --- | --- | --- |
| 卷尺前进距离 | `0.242 m`（约 `24.2 cm`） | 真实纵向位移基准 |
| 卷尺横向位移 | `0.015 m`（约 `1.5 cm`） | 真实横向位移基准 |
| 原始里程计相对增量 | `Δx=0.238052 m`，`Δy=0.010303 m` | 纵向误差约 `1.6%`，通过 |
| EKF 相对增量 | `Δx=0.235924 m`，`Δy=0.033251 m` | 纵向误差约 `2.5%`；`y` 不能直接当作车体横移 |

`/odometry/filtered.pose.pose.position.x/y` 是 `odom` 全局坐标，不是以每次测试
开始时车头方向为 x 轴的局部坐标。本次测试开始时 EKF 航向约为 `0.126 rad`，所以
车辆沿自身 x 轴前进时，前进量会自然投影到 `odom.y`。将 EKF 增量旋转回测试开始
的车体坐标系：

```text
dx_body = cos(yaw0) * dx_odom + sin(yaw0) * dy_odom
dy_body = -sin(yaw0) * dx_odom + cos(yaw0) * dy_odom
```

本次得到 `dy_body≈0.0033 m`；原始里程计对应 `dy_body≈0.0006 m`。因此 EKF 的
`0.033 m` 不是 `3.3 cm` 的实际横向滑移，主要是起始航向投影。不能通过修改轮距、
关闭 `vy` 融合或盲目增大 IMU 协方差来修复，否则会破坏麦轮横移能力或掩盖真正的
坐标基准问题。

重复测试前应先把 EKF 位姿归零。车辆静止且速度已经为零时，调用实际提供的全局
`/set_pose` 服务：

```bash
ros2 service call /set_pose robot_localization/srv/SetPose \
  "{pose: {header: {frame_id: odom}, pose: {pose: {position: {x: 0.0, y: 0.0, z: 0.0}, orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0}}, covariance: [0.0001, 0, 0, 0, 0, 0, 0, 0.0001, 0, 0, 0, 0, 0, 0, 0.0001, 0, 0, 0, 0, 0, 0.0001, 0, 0, 0, 0, 0, 0.0001, 0, 0, 0, 0, 0, 0.0001, 0, 0, 0]}}}"
```

归零后再记录起点和终点，或者按上面的旋转公式换算后再与卷尺比较。当前结论是：
编码器纵向尺度已经修复，EKF 纵向定位通过；横向定位应使用起始车体坐标评估，不能
直接把 Foxglove 中 `odom.y` 的增量当作车辆横向位移。

### 3.3 断线容错测试

运行中拔掉 USB Type-C 串口线：

- 硬件接口 `read()` 检测到串口错误，连续 `max_read_misses`（默认 20）个
  周期无有效帧后返回 `ERROR`。
- controller_manager 记录错误并使硬件进入非活动状态，**进程不崩溃**。
- 重新插线并重启 launch 可恢复。

### 3.4 Web 遥测适配层验证（mock / 实机通用）

该适配层用于规避树莓派实机上 `rosbridge_websocket` 直接序列化
`nav_msgs/msg/Odometry` 时出现的
`cannot serialize type <class 'nav_msgs.msg._odometry.Odometry'>` 异常。
底盘原始话题 `/mecanum_drive_controller/odometry` 仍然保留，但只建议给 ROS
内部调试、录包与算法模块使用；网页侧应改订阅轻量话题 `/web/telemetry/*`。

启动 `smartcar.launch.py` 后，另开终端执行：

```bash
source install/setup.bash

# 1) 两个轻量遥测话题应存在
ros2 topic list | grep '/web/telemetry/'

# 2) 查看消息类型
ros2 topic type /web/telemetry/twist
ros2 topic type /web/telemetry/pose

# 3) 在底盘运动时应能收到消息
ros2 topic echo /web/telemetry/twist --once
ros2 topic echo /web/telemetry/pose --once
```

验证结果（2026-08-05 树莓派实测）：

- [x] `/web/telemetry/twist` 类型为 `geometry_msgs/msg/TwistStamped`。
- [x] `/web/telemetry/pose` 类型为 `geometry_msgs/msg/PoseStamped`，单实例启动时
  有 1 个发布者和 1 个订阅者。
- 当小车前进、横移或旋转时，这两个话题会同步反映平面速度与二维位姿。
- `/mecanum_drive_controller/odometry` 继续可以用 `ros2 topic echo` 观察，说明
  ROS 内部原始里程计链路没有被删除。
- 已在 Web 客户端连接期间观察启动终端，未再出现
  `rosbridge_websocket: cannot serialize type ...`。

网页侧验证要点：

- Web UI 连接 `rosbridge` 后，应订阅 `/web/telemetry/twist` 与
  `/web/telemetry/pose`。
- Web UI 不应再直接订阅 `/mecanum_drive_controller/odometry`。
- 浏览器连接后，`smartcar.launch.py` 所在终端不应再持续出现
  `rosbridge_websocket` 的 `cannot serialize type ... Odometry` 报错。

## 4. USB 单目相机验证

相机只允许由 `usb_cam` 打开稳定别名 `/dev/hik_monocular`。实测在 `1920×1080`
下，MJPEG 支持 `30 fps`，裸格式不足以满足实时感知，因此不得改为裸格式回退。
`usb_cam` 与 `hik_mjpeg_decoder_node` 必须位于同一组件容器，原始 MJPEG 只在进程内的
`/hik_monocular/driver/*` 传递；桥接校验后向可视化发布
`/hik_monocular/image_raw/compressed`，只在感知订阅时才解码
`/hik_monocular/image_raw`（`bgr8`）。独立 `hik_camera.launch.py` 与整车启动
`smartcar.launch.py use_hik_camera:=true` 是单实例关系，必须二选一。

### 4.1 安装、绑定与采集

```bash
sudo apt install -y ros-jazzy-usb-cam ros-jazzy-camera-calibration \
  ros-jazzy-web-video-server ros-jazzy-image-transport-plugins

# 首次部署：仅携带显式开关时才会修改 udev 与内核命令行。
bash scripts/install_hik_camera_system.sh --install-udev --configure-usb-buffer \
  --workspace /home/bean/smart_car_robot
sudo reboot
```

重启后确认别名、唯一序列号和 USB 缓冲参数：

```bash
readlink -f /dev/hik_monocular
udevadm info --query=property --name=/dev/hik_monocular | grep ID_SERIAL_SHORT
udevadm info --query=property --name=/dev/hik_monocular | grep '^ID_V4L_CAPABILITIES=.*capture'
tr ' ' '\n' < /proc/cmdline | grep '^usbcore.usbfs_memory_mb=128$'
```

若最后一条 V4L2 属性检查不含 `capture`，说明别名错误地指向同一相机的
非采集节点。重新执行 `--install-udev` 后重启或重新插拔相机，禁止继续启动
`usb_cam`。

### 4.2 独立启动与频率门槛

启动前确认设备未被其他相机入口占用：

```bash
fuser -v /dev/hik_monocular /dev/video0
ros2 node list | grep hik_monocular
```

若 `Starting 'hik_monocular'` 后出现 `Component constructor threw an exception`，
说明应先排查设备占用。回到占用进程所属终端按 `Ctrl+C` 正常退出，再只启动本节的
独立入口或 §4.4 的整车入口之一。`unknown control` 是 UVC 可选控制项不匹配的
警告；后续出现 `Timer triggering every 33ms` 且组件加载完成时不代表采集失败。

```bash
ros2 launch hik_camera_bringup hik_camera.launch.py \
  use_web_preview:=false

ros2 topic echo --once /hik_monocular/camera_info
ros2 topic hz /hik_monocular/image_raw/compressed
ros2 topic echo --once /hik_monocular/image_raw/compressed --field format
```

连续观察 `60 s` 后，压缩图像平均频率必须不低于 `28 fps`，并且格式必须为 `jpeg`。
树莓派抽样实测 `/hik_monocular/image_raw/compressed` 约为 `30.013 Hz`。使用
`rqt_image_view` 时选择 `/hik_monocular/image_raw` 的 `compressed` 传输（通常显示为
`/hik_monocular/image_raw/compressed`）；不要选择默认 `raw`。未完成标定时，
`camera_info` 的零内参仅用于提示状态，禁止用于感知、几何测量、SLAM 或避障。

### 4.3 可选 Web 预览

```bash
ros2 launch hik_camera_bringup hik_camera.launch.py \
  use_web_preview:=true

curl -sI 'http://127.0.0.1:8080/stream?topic=/hik_monocular/image_raw&width=640&height=360&quality=70&client_id=validation'
ros2 topic hz /hik_monocular/image_raw
```

期望 HTTP 响应为 `200` 且提供 MJPEG multipart。浏览器预览订阅按需 BGR 图像，
仅用于人工观察；`30 fps` 验收仍以压缩 JPEG 话题为准。若出现持续丢帧或 CPU
超标，关闭 `use_web_preview`，只保留 ROS 感知链路。

### 4.4 与总启动集成

```bash
ros2 launch smartcar_bringup smartcar.launch.py \
  use_mock_hardware:=false serial_port:=/dev/ttyUSB0 \
  use_hik_camera:=true use_web_preview:=true
```

默认不启动相机。若相机未连接或服务不可用，应保持 `use_hik_camera:=false`；底盘、IMU、rosbridge `9090` 与控制链路必须独立正常工作。

## 5. 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 发布 `Twist` 无反应 | 控制器只收 `TwistStamped` | 用 `-p stamped:=true` + remap（见 §2.3） |
| 控制器一直 `inactive` | 接口命名不匹配 / URDF 未加载 | 检查 launch 日志中 hardware 加载与关节名 |
| WSL2 上服务查询卡住 | 默认 SHM 发现在 WSL2 不稳定 | 重启后台守护 `ros2 daemon stop`，清理 `/dev/shm/fastrtps_*` |
| 实机方向反了 | 电机接线镜像 | 改对应 `direction_mX` 为 -1 |
| `rviz2` 报 `could not connect to display` | SSH 无 X11 转发 / 无显示服务器 | ① Pi 接了显示器：`export DISPLAY=:0`；② SSH 转发：Windows 装 VcXsrv 后 `ssh -Y user@pi`；③ VNC：`sudo raspi-config` 开启 VNC，Windows 用 VNC Viewer 连接 |
| 摄像机启动在 `Starting 'hik_monocular'` 后报构造异常 | 独立与整车入口并行，或旧相机进程占用设备 | 执行 `fuser -v /dev/hik_monocular /dev/video0`，在占用终端按 `Ctrl+C` 后只启动一个入口 |
| 摄像机无画面 / `:8080` 不通 | 未启动 `web_video_server`、别名未创建或相机未连接 | 见 §4；先验证 `/hik_monocular/image_raw/compressed`，再显式启用 Web 预览 |
